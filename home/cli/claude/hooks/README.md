# claude code hooks

`home/cli/claude/default.nix` installs these to `~/.claude/hooks` as a read-only
store path, `home/cli/claude/settings.json` wires them up. Both need a deploy.
Every rule carries its reasoning next to it in the script, read them there.
`run-tests.sh` is the suite behind `mise run claude-hooks-test`; a change to a
guard or the statusline ships with its cases there. All guards share one
contract: only exit 2 blocks a call, any other exit is non-blocking, so a
payload they cannot parse ends in exit 2 rather than failing open.

| Event | Matcher | Hook |
|---|---|---|
| `PreToolUse` | `Bash` | `bash-guard.sh`, blocks destructive and outward-posting commands |
| `PreToolUse` | `Edit\|Write` | `test-guard.sh`, blocks added skip/only markers |
| `PreToolUse` | `Read` | `read-guard.sh`, blocks reads of `.env` secret files |
| `PostToolUse` | `Bash` | `audit-log.sh`, logs infra mutations, never blocks |
| `SessionStart` | `*` | `herdr-agent-state.sh`, generated by herdr at build time |

## Per project

The global rules stay global, a repo tunes them through files at its root:

- `.claude/outbound-hosts`: bash-guard blocks http writes (POST/PUT/PATCH/
  DELETE, request bodies) everywhere except dev hosts (localhost, loopback,
  `host.docker.internal`, `.test` / `.localhost`). This file names more
  allowed hosts, one per line, `#` comments and blanks skipped. Exact match,
  no suffixes: `api.example.com` does not cover `x.api.example.com`. Found by
  walking up from the session cwd, first hit wins. It only opens the http
  clients, never the forge CLIs, publishing, or mail. Maintained by the user,
  the agent does not add hosts.
- `.claude/settings.json` / `.claude/settings.local.json`: extra allow rules
  for the permission prompts of that project. An allow there never overrides
  a hook block or a global deny, so it cannot reopen what the guards close.
  That is why outbound-hosts is its own file the guard reads directly.
